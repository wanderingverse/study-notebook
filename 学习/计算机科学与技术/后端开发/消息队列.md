# 消息队列
## 消息队列概述
消息队列（Message Queue）是一种用于存取消息的队列。
## 消息队列的应用场景
### 异步处理
如在电商类网站中，新用户注册时需要将用户的信息保存到数据库中，同时还需要额外发送注册的邮件通知以及短信注册码给用户。但因为发送邮件、发送注册短信需要连接外部的服务器，需要额外等待一段时间，此时可以使用消息队列进行异步处理，实现快速响应。
### 系统解耦
如在电商类网站的微服务系统中，订单系统和库存系统是两个独立的微服务，当用户下订单之后，订单系统处理订单，需要与库存系统交互。传统微服务之间通过 API 进行调用，会产生时间耦合（如两方必须同时在线）和接口耦合（如接口参数、格式、协议变更后互相影响）。但这种方式会让两个系统间产生耦合，比如 API 发生变化，请求方和调用方都需要修改。通过消息队列，订单系统将消息发送到消息队列，库存系统从消息队列消费消息，两系统一个生产消息、一个消费消息，各自只对消息负责，解除了两个系统之间存在的耦合：时间解耦（生产者和消费者不必同时在线）和通信方式解耦（不需要直接 RPC 调用），而原有两服务之间的接口耦合则转换为各自对消息的耦合。
### 削峰填谷
在高并发场景下，大量流量和请求瞬时涌入服务器，很容易超过服务器能处理的上限，最终导致服务不可用。使用消息队列作为缓冲区后，所有请求积压在消息队列，排队等待业务处理服务器逐一处理，此时业务系统按自身能力进行消费，保证了服务稳定，避免雪崩、宕机等问题。而在低流量时段，积压在消息队列中的任务可被继续处理，充分利用了资源，稳定保证服务器的处理能力。
### 日志处理
大型网站在分析用户行为时，比如要根据用户的访问行为来发现用户的喜好以及活跃情况，需要收集大量的用户访问信息存储和分析。如果所有分析处理程序都直接从应用服务器获取日志，会造成耦合高、性能瓶颈、扩展困难等问题。引入消息队列，可作为临时存储或者通信管道，用户产生的日志信息由应用服务器发送到消息队列，然后由（众多）实时处理程序从消息队列消费消息并处理。降低了应用服务器的压力，提高了日志分析和处理效率。
## 生产者、消费者模型
### 交互模型
#### HTTP 请求&响应模型
前端发起 HTTP 请求，提交给后端服务器，服务器接收到请求并处理后，返回 HTTP 响应给前端。
通信过程基于 HTTP 协议。
#### 数据库请求&响应模型
客户端程序发送给数据库服务器要处理的 SQL 语句，服务器接收到请求后，返回响应结果。
通信过程基于数据库的通信协议。
#### 生产者&消费者模型
生产者生产消息，并将消息传递到消息队列。
消费者消费消息，从消息队列中取出消息进行处理。
### 消息队列的两种模式
#### 点对点模式
生产者生产消息到消息队列中，消费者从消息队列中取出并消费消息。一条消息一经消费，消息队列中便不再存储该消息，即消费者不可能消费到已经被消费的消息。
特点：
- 每个消息最多只能有一个消费者（Consumer）
- 生产者和消费者之间没有依赖性。生产者生产消息后，无论有没有消费者消费，都不会影响到生产者下次生产消息。
- 消费者在成功接收到消息之后，需向消费队列应答一次成功，以便消息队列删除当前已被接收的消息。
#### 发布/订阅模式
每个消息可以有多个订阅者，一条消息可以被消费多次。
发布者和订阅者之间的消息有时间上的依赖性，一条消息超过一定的时间，订阅者就不能再消费。
针对某个主题（Topic）的订阅者，它必须创建至少一个订阅者之后，才能消费发布者的消息。同理，为消费消息，订阅者需要提前订阅该角色的主题，并保持在线运行。
## 消息队列中间件
消息队列中间件指基于消息队列的、用于存取消息的组件。主流的消息队列中间件有：Kafka、RabbitMQ、RocketMQ 等。

## Kafka 简介
Kafka 是由 Apache 软件基金会开发的一个开源分布式流平台。它能够发布和订阅流数据流（类似于消息队列或者企业消息传递系统）、以容错的持久化方式存储数据流并且处理数据流。
在大数据技术领域，一些重要的组件和框架都支持 Apache Kafka。其成熟度、社区、性能、可靠性都非常有竞争力。
### 应用场景
- 建立实时数据管道，可靠地在系统或应用程序之间获取数据。
- 构建实时流应用程序，以转换或响应数据流。
### 版本
Kafka 版本 ≤ 2.8，必须依赖 ZooKeeper 进行元数据管理。
Kafka 版本 2.8.x ~ 3.x，支持无 ZooKeeper（KRaft），但默认仍可用 ZooKeeper。
Kafka ≥ 3.x，使用 Kafka 自带的 Raft 协议进行元数据管理。
## 环境搭建
### Docker 单机部署 Kafka
#### 拉取 Kafka Docker 镜像
```bash
docker pull bitnami/kafka:latest
```
#### 创建容器并启动
```bash
docker run -d --name kafka \
  -p 9092:9092 \
  -e KAFKA_CFG_NODE_ID=0 \
  -e KAFKA_CFG_PROCESS_ROLES=broker,controller \
  -e KAFKA_CFG_CONTROLLER_QUORUM_VOTERS=0@localhost:9093 \
  -e KAFKA_CFG_LISTENERS=PLAINTEXT://:9092,CONTROLLER://:9093 \
  -e KAFKA_CFG_ADVERTISED_LISTENERS=PLAINTEXT://39.106.10.8:9092 \
  -e KAFKA_CFG_CONTROLLER_LISTENER_NAMES=CONTROLLER \
  -e ALLOW_PLAINTEXT_LISTENER=yes \
  bitnami/kafka:latest
```
- KAFKA_CFG_NODE_ID：指定 Kafka 节点的唯一 ID（KRaft 模式下等同于 `node.id`），要求使用任何非负整数。单节点一般用 `0`，多节点用 `0,1,2...` 且互不重复。
- KAFKA_CFG_PROCESS_ROLES：定义当前 Kafka 进程所承担的角色。`broker`（处理客户端读写）或 `controller`（管理元数据仲裁），可以同时是两者。
- KAFKA_CFG_CONTROLLER_QUORUM_VOTERS：配置 KRaft 集群指定谁是 controller 成员（仲裁者），格式为 `id@host:port`（多个用逗号分隔），与 `node.id` 对应。
- KAFKA_CFG_LISTENERS：定义服务在容器上“监听”的接口与端口，支持多个命名 listener。
- KAFKA_CFG_ADVERTISED_LISTENERS：指定客户端如何连接到 kafka。客户端用这个地址再去建立真实连接。需指定为服务器公网 IP。
- KAFKA_CFG_CONTROLLER_LISTENER_NAMES：指明哪一个 listener 名称用于 controller 通信（必须与 `listeners` 中某个 listener 名称一致）。
- ALLOW_PLAINTEXT_LISTENER：是否允许使用纯文本（PLAINTEXT） listener，而不强制启用 TLS。
#### 验证 Kafka 是否启动成功
```
docker logs -f kafka
```
#### 安装并启动 Kafka UI
```bash
docker run -d --name kafka-ui \
  -p 19092:8080 \
  -e KAFKA_CLUSTERS_0_NAME=local \
  -e KAFKA_CLUSTERS_0_BOOTSTRAPSERVERS=39.106.10.8:9092 \
  provectuslabs/kafka-ui:latest
```
